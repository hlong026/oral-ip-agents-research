## 一、一句话结论

**视频剪辑模块的业务闭环（定稿→发布不可篡改）与合成内核（字幕样式真链路、BGM 闪避、封面自动生成与所见即所得预览）已经打通，并发/幂等/计费/质检工程化程度是全仓库最扎实的部分，接近可上线水位；但"剪辑"名不副实——它实际是一个"发布内容定稿台"，产品蓝图中的差异化卖点（防判重随机化、多画幅导出、BGM、文本驱动剪辑、V2 工作台）均未兑现，前端 UI 停留在 V1 旧布局，且最新一次提交（HEAD）存在缺 import 疑似挂 CI、定稿后双字幕等赶工质量问题。**

## 二、模块定位与业务链路

### 2.1 业务定位

产品文案称"视频剪辑"（流水线第⑥步 `edit`），但代码自述与实际能力是"**成片发布定稿台**"（`apps/web/src/pages/EditorPage.tsx` 注释）。其业务价值不是通用剪辑，而是：

1. 把合成产出的**无字幕干净母版**（clean master）作为可反复精修的底稿；
2. 在剪辑台完成字幕校对/样式、标题+标签、封面三件套的编辑与 AI 辅助；
3. 通过 `finalize` 生成**不可变的定稿版本**（`PublicationRevision`），发布环节只消费定稿版本 ID，彻底杜绝"发出去的内容和用户看到的不一致"。

这与 `docs/16-发布内容定稿V1实施规格.md` 的设计完全一致，9 条硬不变量（合成不烧字幕、定稿不可改、定稿幂等不重复扣费、失败保旧、发布固定版本、无干净母版拒绝二次烧字幕防双字幕等）在后端均有实现和测试背书。

### 2.2 端到端链路（实测代码走向）

```
CreatePage 七步向导（⑤视频合成产出 final_video_key + clean_video_key）
  → StepEdit「进入剪辑台」 → /editor?task=<id>            (CreatePage.tsx:1019)
EditorPage
  ① GET /pipelines/{id}/publication-draft  后端无草稿则自动创建，
     segments 由服务端从 tts_words/words 切句生成         (pipeline/service.py:504-525, 1349-1408)
  ② 编辑标题/标签/字幕/封面 → 700ms debounce 自动存草稿（draftRevision CAS 乐观锁）
  ③ 「合成最终视频」→ 报价(hd_export 3积分/次) → POST /finalize（幂等键 + 积分冻结）
  ④ 渲染 worker (render.py:run_render_version)：渲染→质检→结算→原子切换活动版本
     revision: draft → rendering → finalized（失败回 draft 并退积分）
  → /publish/jobs?task=<id>&revision=<rev>  发布只读定稿版本，不可再改
```

发布侧强约束（`pipeline/engine.py:650 step_publish`）：质检不过禁止发布；无 finalized revision 则 skip；标题/话题/视频/封面全部取自定稿版本。

### 2.3 技术路线

`docs/04-视频合成模块调研与技术选型报告.md` 选定 **路线 B：FFmpeg 子进程 + Python 编排层自建**（零授权成本、与数字人链路耦合、单条合成成本 ≈¥0–0.02），明确排除 Remotion（商业授权风险）、云剪辑 API 仅作兜底。`docs/15-开源视频剪辑项目调研报告.md` 进一步确认不引入任何重型第三方剪辑运行时，仅建议引入轻量库（pysubs2）+ 移植成熟实现（MoneyPrinterTurbo 的字形覆盖检测/像素级换行）。**选型判断本身是合理的**，与"合成不是成本中心，效果与差异化才是竞争力"的结论自洽。

## 四、计费与商业闭环

- 定稿渲染按 `hd_export` 模块计费：**3 积分/次（per_action）**（`catalog/service.py:45`）；流水线整单由服务端重建用量报价（`billing/service.py:453`），必含 tts+digital_human+hd_export，防止前端删减模块少付费。
- 冻结→结算→退款链路完整：finalize 时 `reserve_quote` 预扣，渲染成功 `settle_reservation`，失败 `release_reservation`/`recover_reservation_after_failure`（含另开独立 Session 的兜底释放），并有专门回归测试锁定"只结算一次""失败保留已付费成片"等语义。
- **体验缺陷**：前端 `confirmMeteredOperation`（`apps/web/src/lib/meteredOperation.ts:69`）名为 confirm 实际不弹确认框，注释称"费用信息由页面内联展示"，但 EditorPage 并**没有**内联展示价格——用户点击"合成最终视频"即被直接扣 3 积分，全程看不到费用。对按积分付费的商业模式，这是投诉风险点。

## 五、质量与风险清单（按严重度）

### 🔴 高危

1. **HEAD 提交疑似挂 CI**：`EditorPage.tsx:44/51/100` 使用 `SubtitleSegment` 类型，但文件顶部 `import type` 块（:3-10）未导入，全仓亦无全局声明（该类型仅由 `packages/types/src/index.ts:419` 导出）。`apps/web` 的 build 含 `tsc --noEmit`，CI 有 `pnpm typecheck`。**已实跑确认为红**：`pnpm typecheck` 在该提交上报 10 个错误——2 个 `TS2304: Cannot find name 'SubtitleSegment'`，外加 `buildSubtitlesFromAsrWords` 内部 8 个 strict 模式 `possibly undefined`。
2. **定稿后双字幕**：finalize 后新成片已烧录字幕且 `final_video_url` 更新，但预览 overlay（`EditorPage.tsx:687`）无 finalized 判断仍继续渲染 HTML 字幕 → 视频内烧录字 + 页面浮层字同时出现。
3. **WYSIWYG 与成片行为不一致**：前端 `activeSubtitle`（:593-597）只按 `startMs` 取"最后一句"，忽略 `endMs`——句间停顿时预览仍显示上一句，而后端 ASS 按真实 start/end 区间烧录；字号映射 `fontSize / 2.2`（:702）为魔法数，与 FFmpeg 实际渲染无对应关系。
4. **`storage.exists()` 在 S3 驱动下无条件返回 True**（`core/storage.py:138-141`）：`CLEAN_MASTER_MISSING` 与封面候选缓存有效性检查在生产 S3 部署下形同虚设——防双字幕的关键前置校验在生产环境失效。

### 🟠 中危

5. **前后端重复且规则不一致的切句逻辑**：HEAD 新增的 `buildSubtitlesFromAsrWords`（前端，300ms 间隔合并）与服务端 `_default_publication_content`（0.5s 断句+标点+16 字）各写一套；且由于后端 GET publication-draft 总是自动建草稿，前端这套在正常路径**永不执行**，近似死代码。
6. **长视频字幕静默截断**：前端兜底路径 `segments.slice(0, 20)`（`EditorPage.tsx:128`）硬截 20 句，无任何提示。
7. **`openapi.snapshot.json` 过期**：缺 `POST /pipelines/{id}/cover-preview`（commit `c352062` 新增后未重生成），双端类型靠手写镜像（`types/index.ts` vs `generated.ts`）人工同步，漂移风险高。
8. **遗留死代码**：`pipelineApi.recompose`/`renderVersions`/`EditConfig` 是上一代剪辑方案残留，生产代码无调用，仅测试 mock 引用。
9. **EditorPage 技术债扩大**：审计报告（`docs/代码结构深度审计报告.md`）时 1079 行、P1 要求本月拆分，现已 1201 行仍是单文件（13 个 useState + 8 个 useRef 影子副本），拆分未执行反在膨胀。顺带指出：该审计报告称 EditorPage 含"FFmpeg 配置/多轨道混剪"，与实际代码不符，审计描述本身注水。
10. **`step_edit` 判定脆弱**（`engine.py:635`）：`has_config` 把 `bgm_mode=="off"` 也算"有配置"，任何写过 edit_config 的任务都会触发一次重新合成。

## 七、分析结论

1. **业务架构判断正确且已兑现**：把"剪辑"重定义为"发布前定稿"是符合口播场景的（用户要的是快速出片+发布安全，不是时间线剪辑），定稿不可变+发布固定版本的闭环是本模块最大的业务资产，工程质量（CAS 并发、幂等、计费对账、质检门禁、失败退款）在全仓库属最高水位，**该部分接近可上线**。
2. **"剪辑"能力与产品叙事存在实质落差**：需求清单和技术选型文档承诺的差异化竞争力——批量防判重随机化（F-406）、多画幅多平台（F-404/CoverSpec）、BGM 闪避（F-402）、文本驱动剪辑——目前要么零实现、要么后端就绪但被前端/类型层封死。若近期有对外演示或售卖动作，需明确管理预期：现阶段可承诺的是"自动出片+字幕/封面/标题精修+安全发布"，不是"剪辑"。
3. **最新提交引入了可见的质量回退**：已实跑确认挂 CI 的缺 import、定稿后双字幕、预览与成片不一致、零测试——这些会直接伤害"所见即所得"这一卖点本身，应在继续堆功能前先止血。同一提交还把 dramatiq actor 的重试参数写成了不存在的 `retry_interval`，使全部流水线任务无法入队（详见第九节 #5），说明该提交未经任何本地验证即合入。
4. **生产隐患集中在 S3 路径**：`storage.exists()` 恒 True 使防双字幕的关键校验在生产存储驱动下失效，与 dev（local 驱动）行为不一致，属于"测试全绿但生产会漏"的典型。
5. **过程资产与现实开始脱节**：openapi 快照过期、审计报告描述失实、docs/20 中 V-02 实际已完成——文档驱动开发是本仓库的优势，但需要回写机制，否则后续决策会基于过期信息。
