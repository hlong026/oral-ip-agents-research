## 三、P0 — 阻塞生产，立即推进

### 3.1 方案 E 阶段 1：真机验证（负责人：用户）

- **问题**：WebView 嵌入抖音官方页未做真机验证，不确定是否被环境检测拦截
- **操作**：`cd apps/desktop && pnpm tauri:dev` → 私信中心点"在抖音回复（新窗口）" → 真实账号扫码登录
- **验收**：能加载抖音页、能登录、能看到消息列表、能打开会话并发送回复；关闭重开登录态保持
- **预估**：0.5 天
- **失败回退**：若被检测拦截，尝试加真实 Chrome UA；若仍不行，退回 `window.open` 用系统浏览器

### 3.2 修复 listener 状态机自锁

- **问题**：监听失败 5 次后置 `error` 态并退出，`reconcile_listeners` 只拉 `status=="listening"`，**网络恢复也不自愈**，需人工改状态
- **证据**：`server/app/workers/im_listener.py:382-387`（失败退出）、`:144`（reconcile 只查 listening）
- **方案**：reconcile 纳入 `error` 态，按指数退避（max 1h）自动重试；提供 admin 手动 reset 接口作兜底
- **涉及文件**：`im_listener.py`、`server/app/modules/im/repository.py`（可能加 reset 方法）
- **验收**：断网触发 error 后，恢复网络，listener 在指数退避内自动恢复 listening；新增单测覆盖 error→listening 回迁
- **预估**：1 天
- **依赖**：无，可与 3.1 并行

### 3.3 解除 `config.py` 生产 No-Go（⚠️ 合规代码，需确认）

- **问题**：`config.py:138-139` 无条件阻断生产环境 `im_enabled=True`（第三阶段合规结论 No-Go）。原意是阻止不可靠发送，但现在方案 E 不发送，阻断过时
- **方案**：新增 `im_listen_only: bool = True` 开关。该模式下放宽 No-Go：允许生产启用 IM，但强制 provider 层 `send_message` 保持 fail-closed、自动回复不触发发送
- **合规依据**：读取自己账号私信（cookie 鉴权 WebSocket）不产生对外行为，风险等级远低于模拟发送
- **涉及文件**：`server/app/core/config.py`
- **验收**：`im_listen_only=true` 时生产可启用监听；任何发送路径被拒并记日志；新增单测锁定"只读模式下 send 必失败"
- **预估**：0.5 天
- **前置**：⚠️ 涉及合规阻断解除，改前出 diff 人工审查

### 3.4 方案 E 阶段 2：多账号 session 隔离

- **问题**：当前所有账号共用单一 `douyin-webview` data 目录，多账号登录态会串
- **方案**：按 `account_id` 分配独立 `data_directory`（`app_data_dir/douyin-webview/{account_id}`）；ImCenterPage 按选中会话的 account 切换 WebView
- **涉及文件**：`main.rs`（`open_douyin_im` 接收 `accountId` 参数）、`douyinWebview.ts`、`ImCenterPage.tsx`
- **验收**：账号 A 登录后切到账号 B，B 需独立登录，互不串；A 重开仍保持 A 的登录态
- **预估**：1-2 天
- **依赖**：3.1 验证通过

### 3.5 方案 E 阶段 3：清理方案 D 发送残留（保留监听）

- **问题**：发送相关代码（fail-closed 占位、发送端点、发送队列、前端发送框、build/lib 伪实现）与新方案 E 矛盾，留着误导
- **🔴 边界红线**：发送与监听**共用** `douyin_im.py` 与 config。只删"发送专用"，**绝不能动** connect/listen/`_decode_frame`/proto/config
- **清理范围**：
  - `server/app/providers/im/douyin_im.py`：删 `send_message`、`create_conversation`
  - `server/app/modules/im/router.py`：删 `/send`、`/messages/{id}/retry`、`/messages/{id}/takeover` 端点
  - `server/app/modules/im/service.py`：删 `send_message`、`retry_message`、`take_over_message` 及发送队列调度
  - `apps/web/src/pages/ImCenterPage.tsx`：删发送输入框与发送逻辑（保留"在抖音回复"按钮）
  - `server/build/lib/app/providers/im/douyin_im.py`：删早期 JSON 伪实现版本
  - `docs/07` 任务书：发送/a_bogus/自动回复发送章节标注"已由方案 E 取代"
- **保留**：`connect`、`listen`、`_decode_frame`、`proto/v1/*`、`config.py` 的 `im_*` 配置、会话/消息模型与列表 API
- **验收**：监听聚合功能不受影响（收消息、看会话正常）；任何发送入口已移除或改为"打开抖音"；现有 IM 单测全绿
- **预估**：1 天
- **前置**：**先出详细清理清单确认，再动手**（发送 vs 监听边界必须逐项核对）

## 八、风险与注意事项

1. **合规底线（不可逾越）**：方案 E 嵌入官方网页后，**严禁注入 JS 自动填表/自动点发送/批量自动回复**。一旦注入自动化，立即回到 ToS 违规 + 风控。允许的辅助仅限：展示官方页、UID/昵称带入剪贴板、侧栏显示 LLM 建议供用户复制。
2. **3.3 No-Go 解除**属合规代码，改前必须人工审查 diff。
3. **3.5 清理**的发送/监听边界必须逐项核对，误删监听会导致整个私信功能失效。
4. **抖音 WebView 检测**是真机验证的最大不确定项（3.1），需准备 UA 适配回退方案。
