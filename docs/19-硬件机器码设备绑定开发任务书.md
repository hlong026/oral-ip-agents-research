> 涉及端：server（FastAPI）、apps/web（用户端）、apps/admin（管理端）、apps/desktop（Tauri 壳）、packages/api-client

---

## 1. 背景与目标

### 1.1 现状问题

当前设备绑定为**单设备 + 软指纹**方案，存在三个结构性缺陷：

| # | 问题 | 根因 |
|---|------|------|
| 1 | 清浏览器数据 / 换浏览器 / 重装系统后被判"新设备"锁死 | 指纹主键是 `localStorage` 里的随机 UUID（`packages/api-client/src/fingerprint.ts`），不是硬件标识 |
| 2 | 只能绑 1 台设备，换电脑必须找管理员解绑 | `users.device_fingerprint` 是单字段（`server/app/modules/auth/models.py` L33） |
| 3 | 被锁死后用户无自助恢复路径，体验为"账号数据丢失" | 无绑定申请/审批流，只有管理端 `POST /users/{id}/unbind-device` 全量解绑 |

### 1.2 目标方案（一句话）

**桌面端用硬件机器码作为设备标识**（清缓存/重装不变），**每账号支持绑定 N 台设备**（N 由管理员在后台配置），**超出上限时新设备登录被拒并自动生成绑定申请，由管理员审批解绑旧设备后放行**。

### 1.3 不在本期范围

- 手机号/邮箱补绑作为长期身份凭证（后续迭代）
- 并发在线数限制（多设备可同时在线，仅限制绑定总数）
- Windows/Linux 桌面端实测（代码按三平台实现，本期仅 macOS 验收）

## 2. 总体设计

### 2.1 设备标识分层

指纹格式**保持现有** `{设备段}.{特征哈希前16位}` 不变，仅替换桌面端"设备段"的来源：

| 运行环境 | 设备段来源 | 稳定性 |
|---|---|---|
| Tauri 桌面壳 | **硬件机器码**：`hw-{SHA256(原始机器码+盐)[:32]}` | 清缓存/重装应用/重装浏览器均不变；仅重装操作系统或更换主板会变化 |
| 普通浏览器 | 现有 localStorage UUID（降级兜底） | 不变（网页端无法取硬件信息，保持现状） |

原始机器码按平台获取（在 Rust 侧实现，前端只拿哈希结果，**原始值不出 Rust 层**，避免硬件序列号泄露到 Web 上下文/日志）：

- macOS：`IOPlatformUUID`（`ioreg -rd1 -c IOPlatformExpertDevice` 解析）
- Windows：注册表 `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid`
- Linux：`/etc/machine-id`

哈希盐固定为常量 `"oral-ip-device-v1"`（写死在 Rust 代码中；目的不是保密而是让哈希域与其它产品隔离）。

**服务端匹配逻辑零改动**：`fingerprint_matches`（`auth/service.py` L29）本就只严格比较 `.` 前的设备段、容忍特征哈希漂移，`hw-xxxx` 作为设备段天然兼容。

### 2.2 数据模型：单字段 → 设备列表

```
新表 user_devices
├── id            String(32) PK（new_id）
├── user_id       String(32) FK → users.id，索引
├── fingerprint   String(128) 完整指纹（含特征哈希段）
├── device_name   String(64)  展示名，如 "macOS · Tauri 桌面端" / "Chrome · 网页端"
├── source        String(16)  "desktop-hw" | "web"（按设备段是否 hw- 前缀判定）
├── created_at    DateTime(tz)
└── last_seen_at  DateTime(tz)  每次登录/刷新时更新

唯一索引 uq_user_devices_user_fp (user_id, 设备段)   ← 设备段 = fingerprint 按 "." 切分后首段
    实现上存冗余列 device_key String(64)（设备段），唯一索引建在 (user_id, device_key)

新表 device_bind_requests
├── id             String(32) PK
├── user_id        String(32) FK，索引
├── fingerprint    String(128) 申请绑定的新设备指纹
├── device_name    String(64)
├── status         String(16) "pending" | "approved" | "rejected"
├── created_at     DateTime(tz)
├── resolved_at    DateTime(tz) 可空
└── resolved_by    String(32)  可空（管理员 user_id）

部分唯一索引：(user_id, device_key) WHERE status='pending' —— 同一新设备只保留一条待审申请
```

`users.device_fingerprint` 列**保留但废弃**（本期停止读写，避免破坏性 DDL；下期清理）。

Alembic 数据迁移：建两张新表 + 将存量 `users.device_fingerprint` 非空值搬入 `user_devices`（device_name 填 "历史绑定设备"，source 按前缀判定，created_at/last_seen_at 取当前时间）。

### 2.3 可配置绑定上限

- 配置键 `device_bind_limit`，存 `provider_config` 表，走现有 `dynamic_config.get_config()`（60s 缓存）读取
- `settings/router.py` 的 `ALLOWED_KEYS` 增加该键；校验规则：整数、范围 1~10；**默认值 1**（未配置时与现行为一致）
- 管理端 UI：`apps/admin` UsersPage 顶部新增「安全策略」卡片，含"每账号可绑定设备数"输入框（读写 settings API）

### 2.4 登录/刷新流程（核心状态机）

`_login_bound_user`（`activation/service.py` L248）改造：

```
激活码登录（已使用码）
│
├─ 取该用户 user_devices 列表
│
├─ 新指纹设备段 ∈ 列表 ────────────→ 登录成功
│      └─ 特征哈希漂移 → 更新该行 fingerprint + last_seen_at（保留现有 warning 日志）
│
├─ 不在列表 且 列表数 < device_bind_limit
│      └─ 自动新增 user_devices 行（沿用"空即绑"哲学）→ 登录成功
│         审计事件 device_auto_bound
│
└─ 不在列表 且 列表数 ≥ device_bind_limit
       ├─ upsert device_bind_requests（pending，幂等）
       └─ 403 DEVICE_LIMIT_REACHED
          message: "该激活码已绑定 {n} 台设备达到上限，已提交新设备申请，请联系管理员审批"
```

- 首次激活（未使用码）：开户后直接写入第一条 `user_devices`，不再写 `users.device_fingerprint`
- `auth/service.py` 的 `refresh`（L88）同步改为对照 `user_devices` 列表校验；设备被解绑后 refresh 立即失效（配合现有 `RefreshSession.revoked`）
- 403 错误码 `DEVICE_MISMATCH` 语义收窄为"设备已被解绑"（refresh 场景），登录场景统一用 `DEVICE_LIMIT_REACHED`
- 申请创建复用 `activation/rate_limit.py` 现有限流（防刷申请）

### 2.5 管理端审批流

**后端新增端点**（挂 `admin/router.py`，均 `require_admin`）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/device-requests?status=pending&page=&pageSize=` | 申请列表（关联返回用户掩码激活码、当前设备列表）|
| POST | `/admin/device-requests/{id}/approve` | body `{ "unbindDeviceId": "..." }`：解绑指定旧设备（删 user_devices 行 + 吊销该 device 的 RefreshSession）→ 标记 approved。旧设备腾出名额后，新设备**下次登录自动绑定**（复用 2.4 自动绑定分支，无需为新设备预写记录）|
| POST | `/admin/device-requests/{id}/reject` | 标记 rejected |
| GET | `/admin/users/{user_id}/devices` | 该用户设备列表（device_name、source、created_at、last_seen_at）|
| POST | `/admin/users/{user_id}/devices/{device_id}/unbind` | 单设备解绑（删行 + 吊销对应会话）|

- 现有 `POST /users/{user_id}/unbind-device` **保留**，语义升级为"解绑全部设备"（清空 user_devices + 吊销全部会话），兼容既有管理端按钮
- 审批时若 `unbindDeviceId` 为空且当前设备数已 < 上限（比如管理员先手动解绑过），直接标记 approved
- 所有动作写 `write_audit`：`device_request_approved` / `device_request_rejected` / `admin_device_unbound`（detail 带 target 设备段前 8 位，不落完整指纹）

**管理端 UI（apps/admin）**：

1. UsersPage 用户行新增「设备」列（`deviceBound` 布尔改为 `deviceCount/limit`，如 `2/3`），点击弹设备列表抽屉：每台设备展示名称/来源/最近活跃，带"解绑"按钮（现有确认交互模式）
2. 新增「设备审批」入口：ActivationPage 增加 Tab 或侧边栏新菜单项「设备审批」（决策：**放 ActivationPage 新 Tab**，与激活码运营同上下文，避免加导航项）；待审列表每行展示：用户（掩码激活码）、申请设备名、时间、该用户当前设备列表（单选要解绑的旧设备）+「批准并解绑所选」「拒绝」两个按钮
3. UsersPage 顶部「安全策略」卡片：设备上限配置（见 2.3）

### 2.6 桌面端（Tauri）改造

`apps/desktop/src-tauri/src/main.rs` 新增 command：

```rust
#[tauri::command]
fn machine_code() -> Result<String, String> {
    // 按平台取原始机器码 → SHA256(raw + "oral-ip-device-v1") → "hw-" + hex 前 32 位
    // 任一步失败返回 Err，前端降级 localStorage UUID
}
```

- Cargo 依赖新增 `sha2`（纯哈希，无重依赖）
- `invoke_handler(tauri::generate_handler![machine_code])`
- **capability 注意**：正式壳加载本地 dist，IPC 默认可用，`capabilities/default.json` 无需放宽；本地联调壳（`tauri.localdev.conf.json`）加载远程 `http://localhost:5173`，远程 origin 默认无 IPC 权限，需在该 overlay 配置中增加 remote capability（仅 localdev 文件，**不动正式配置**）：

```json
"app": { "security": { "capabilities": [ { "identifier": "localdev-remote", "windows": ["main"], "remote": { "urls": ["http://localhost:5173"] }, "permissions": ["core:default"] } ] } }
```

**前端接入**（`packages/api-client/src/fingerprint.ts`）：

```
deviceFingerprint():
  1. 若存在 window.__TAURI_INTERNALS__ → 动态 invoke("machine_code")
     成功 → 设备段 = 返回值（hw-xxxx）
     失败/超时(1s) → 落到 2
  2. 降级：现有 localStorage UUID 逻辑（原样保留）
  3. 拼接特征哈希段，缓存返回（现有逻辑不变）
```

- 不引入 `@tauri-apps/api` 依赖，直接调 `window.__TAURI_INTERNALS__.invoke`（避免 api-client 增加桌面端依赖；类型用局部声明）
- **迁移体验**：桌面端存量用户指纹从 `uuid.xxx` 变为 `hw-xxx.xxx`，首次登录会被判"新设备"。因存量库仅个位数测试用户，**不做静默换绑**，靠"上限内自动绑定/管理员审批"自然过渡（把 device_bind_limit 先配为 2 即可无感迁移）

### 2.7 用户端提示（apps/web）

## 4. 测试计划

### 4.1 后端 pytest（新增 `test_device_binding.py`）

1. 首次激活自动写入第一台设备；重复登录同设备段（特征哈希漂移）→ 成功且更新指纹
2. 上限内新设备登录 → 自动绑定，设备数 +1，审计事件存在
3. 达上限新设备登录 → 403 DEVICE_LIMIT_REACHED + pending 申请生成；重复登录不产生重复申请（幂等）
4. 管理员 approve（带 unbindDeviceId）→ 旧设备行删除、旧设备 RefreshSession 吊销、申请 approved；新设备再登录 → 自动绑定成功
5. reject → 新设备再登录仍 403（重新生成 pending 申请）
6. 单设备解绑后该设备 refresh 失效（DEVICE_MISMATCH）
7. unbind-device（全量）→ 设备清空，任意设备可重新首绑
8. device_bind_limit 配置：非法值（0、11、非整数）保存被拒；调低上限后存量超额设备**不被踢**（只影响新增绑定）
9. 迁移测试：存量 users.device_fingerprint 正确搬入 user_devices

### 4.2 前端

- api-client：fingerprint 在无 Tauri 环境走 localStorage 路径（现有行为回归）；mock `__TAURI_INTERNALS__` 走 hw 路径与降级路径
- admin：审批 Tab 渲染、approve/reject 调用、安全策略卡片读写（vitest）

### 4.3 桌面端手动验收（macOS）

1. 桌面壳登录 → 管理端设备列表出现 `hw-` 前缀、source=desktop-hw 的设备
2. **关键场景**：清空 WebView 缓存/localStorage 后重新打开 → 仍判定同一设备，直接登录成功（这就是"数据不再丢失"的验收标准）
3. 同一激活码在浏览器（网页端）登录 → 占用第二个设备槽（上限 ≥2 时）
4. 达上限后第三端登录 → 提示语正确；管理端审批解绑后重登成功

## 5. 风险与边界说明

| 风险/边界 | 说明与对策 |
|---|---|
| 重装操作系统 / 换主板 | macOS IOPlatformUUID 会变 → 判新设备。属预期行为，走上限自动绑定或审批流恢复，**不会死锁** |
| 网页端仍是软指纹 | 浏览器无法取硬件码，清缓存仍会占新槽位。但多设备 + 审批流兜底，最坏情况是找管理员，不再是死锁 |
| localdev 壳远程 IPC | 仅在 localdev overlay 开放 `http://localhost:5173` 的 IPC，正式配置不受影响，发布检查脚本无需改动 |
| 指纹原文隐私 | 机器码原始值不出 Rust 层；审计日志只落设备段前 8 位 |
| 存量桌面用户指纹切换 | 上线前把 device_bind_limit 配为 ≥2，自动无感换绑；下期再清理废弃行 |
| 激活码明文丢失 | **本方案不解决**（见 §6），属身份凭证问题而非设备问题 |

## 6. 关于"是否不再出现数据丢失"的结论

首先澄清：**业务数据（声音、视频、积分）一直存在服务端，从未真正丢失**——过去"丢失"的是*访问入口*（设备被误判 + 无恢复路径）。本方案后：

✅ **彻底解决**：
- 桌面端清缓存/重装应用/重装浏览器 → 机器码不变 → 不再误判新设备（4.3-2 为验收标准）
- 单设备锁死 → 多设备上限 + 自动绑定，换电脑不再必然找管理员
- 锁死无出路 → 任何"新设备被拒"都自动生成审批申请，管理员审批即恢复，**不存在无解状态**

⚠️ **仍存在、但已从"死锁"降级为"可恢复"**：
- 重装操作系统/换主板 → 判新设备 → 走自动绑定或审批流恢复
- 网页端清浏览器数据 → 占新设备槽 → 同上

❌ **本方案不覆盖**（需下期"手机号补绑"迭代）：
- 激活码明文本身丢失：登录凭证仍是激活码，明文丢了任何设备都无法发起登录。请提醒用户妥善保存，或排期身份凭证补绑功能
