# 15 - 开源视频剪辑项目调研报告

> 调研日期：2026-07-27
> 调研方式：GitHub 仓库检索 + 核心项目源码抽查（License、活跃度、实现方式均已逐项核实）
> 调研目标：为《14-视频剪辑方案-封面与字幕系统设计》寻找可复用的开源项目/库，聚焦四个方向——**字幕标题样式、封面模板、视频模板、画面切换（转场）效果**。

---

## 1. 调研总览

| 方向          | 结论一句话                                                                                                  |
| ------------- | ----------------------------------------------------------------------------------------------------------- |
| 字幕/标题样式 | 有直接可用的库（pysubs2）+ 可抄实现的标杆（MoneyPrinterTurbo），成本最低、收益最大                          |
| 封面模板      | **没有现成的开源"视频封面模板"项目**，可行路线是"HTML/Canvas 模板 → 图片渲染"生态（satori / html-to-image） |
| 视频模板      | editly 的声明式 JSON schema 最值得借鉴；Remotion 能力最强但有商业许可风险                                   |
| 转场效果      | 首选 FFmpeg 内置 `xfade`（零新依赖，约 50 种转场），gl-transitions 做效果参考库                             |

结合本项目现状（后端 Python + FFmpeg 子进程合成链路 `FFmpegCompose`，前端 React，方案 14 已定 CoverSpec 分层建模与 `_build_ass()` 参数化路线），本次调研的总体判断是：

- **不引入任何重型第三方剪辑运行时**（Remotion / FFCreator / editly 整体引入均不划算）；
- **引入轻量库 + 移植成熟实现**：pysubs2 管 ASS 生成，xfade 管转场，MoneyPrinterTurbo 的字幕渲染细节直接移植；
- **封面与视频模板走自建 schema 路线**，分别借鉴 satori/html-to-image 生态与 editly 的 JSON 设计。

## 2. 字幕 / 标题样式方向

### 2.1 候选项目清单

| 项目                                                                | Stars | License           | 语言   | 关键能力                                                                                      | 与本项目的关系                                                |
| ------------------------------------------------------------------- | ----- | ----------------- | ------ | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| [MoneyPrinterTurbo](https://github.com/harry0703/MoneyPrinterTurbo) | 99k   | MIT               | Python | MoviePy TextClip + PIL 字幕渲染：圆角背景条、按可见像素居中、字体字形覆盖检测、像素级精确换行 | **实现思路直接可抄**，同为 Python 栈，活跃维护中              |
| [pysubs2](https://github.com/tkarabela/pysubs2)                     | 435   | MIT               | Python | ASS/SRT/VTT 字幕文件读写库，Style 对象化建模                                                  | **建议直接引入**，替代 `_build_ass()` 手写字符串拼接          |
| [FunClip](https://github.com/modelscope/FunClip)（阿里）            | 6k    | MIT               | Python | FunASR 语音识别 + 词级时间戳 + LLM 辅助剪辑                                                   | 词级时间戳能力可支撑方案 14 的卡拉OK逐字动画（ASS `\k` 标签） |
| [captacity](https://github.com/unconv/captacity)                    | 139   | MIT               | Python | Whisper 词级时间戳 + TikTok 风格大字幕烧录                                                    | 代码量小、结构清晰，逐字高亮的参考实现                        |
| AI-Youtube-Shorts-Generator                                         | 4.3k  | **无 License** ⚠️ | Python | 长视频转短视频 + 高亮字幕                                                                     | 只可看思路，**不可引用任何代码**                              |

### 2.2 源码抽查结论（MoneyPrinterTurbo `app/services/video.py`，1373 行）

抽查确认其字幕实现解决了几个方案 14 落地时必然会踩的坑，对应逻辑均可移植：

1. **字体字形覆盖检测**（`subtitle_font_supports_text()`）：用 `PIL.ImageFont.getmask()` 逐字符比对缺字掩码，用户选择的字体不支持中文/生僻字时自动降级到兜底字体，避免渲染出"豆腐块"。
2. **像素级精确换行**（`wrap_text()`）：在创建 TextClip 之前用 `font.getbbox()` 按真实像素宽度换行，而非按字符数估算——中英文混排时按字符数换行必然溢出。
3. **可见像素居中**（`_get_visible_center_position()`）：TextClip 的透明画布受字体行高和 baseline 影响，直接 `center` 会导致字幕视觉偏上/偏下；它读取文字真实可见像素的包围盒做居中修正。
4. **圆角背景条**（`_rounded_subtitle_background_clip()`）：独立背景层实现字幕背景条，与方案 14 的"底衬样式"预设对应。
5. 转场在 clip 级实现（fade/slide/zoom/shuffle 六种，MoviePy effects），是转场的另一条低成本参考路径（见 §5）。

### 2.3 落地建议（对应方案 14 §4 字幕系统）

- **P0**：引入 `pysubs2`（纯 Python、MIT、无传递依赖负担）重写 `_build_ass()`。Style 对象化后，6 款预设 + 8 维参数（字体/字号/颜色/描边/背景/位置/动画/关键词高亮）变成填字段，不再拼 ASS 字符串，出错率与维护成本大幅下降。
- **P0**：移植 MoneyPrinterTurbo 的字形检测与像素换行两段逻辑（各约 30-50 行，MIT 许可，保留来源注释）。
- **P1**：卡拉OK逐字动画依赖 ASR 词级时间戳。若现有 ASR 供应商不提供词级粒度，可参考 FunClip（FunASR）或 captacity（Whisper `word_timestamps=True`）补一条本地词级对齐链路。

## 3. 封面模板方向

### 3.1 关键结论

多组关键词检索（poster generator / cover template / html to image poster 等）均无有效结果——**GitHub 上不存在可整体复用的"视频封面模板"开源项目**。业界的实际做法是**用网页技术做模板，再渲染成图**，这印证了方案 14 的 CoverSpec 自建路线是正确的：封面模板本质是结构化数据 + 渲染引擎，没有现成轮子。

### 3.2 可复用的渲染生态

| 项目                                                     | Stars | License | 用法                                                                 |
| -------------------------------------------------------- | ----- | ------- | -------------------------------------------------------------------- |
| [satori](https://github.com/vercel/satori)（Vercel）     | 13.7k | MPL-2.0 | JSX/CSS 子集 → SVG → PNG，服务端渲染、无浏览器依赖（需 Node 运行时） |
| [html-to-image](https://github.com/bubkoo/html-to-image) | 7.2k  | MIT     | 浏览器内 DOM → PNG，前端所见即所得导出                               |
| [OpenCut](https://github.com/OpenCut-app/OpenCut)        | 79k   | MIT     | CapCut 开源替代（TypeScript），封面/文字编辑的 UI 交互参考           |

### 3.3 落地建议（对应方案 14 §3 封面系统）

维持 CoverSpec 分层建模 + RatioLayout 查表路线不变，**渲染端**给出两个可选实现：

- **方案 A（简单稳妥，推荐先做）**：服务端 Pillow 按 CoverSpec 绘制（方案 14 原案）。零新依赖，风险最低；代价是前端 Canvas 预览与服务端 Pillow 定稿需要维护两套渲染逻辑的一致性。
- **方案 B（一致性最好）**：封面模板写成 React 组件——前端用 `html-to-image` 做所见即所得预览与导出；服务端用 Playwright（**项目已有该依赖**，e2e 在用）加载同一组件截图定稿。双端**像素级一致**，模板迭代只改一处；代价是合成流水线中多一次无头浏览器渲染（单张封面约 1-2 秒）。
- satori 仅在愿意为封面渲染增加 Node sidecar 服务时才考虑，当前不推荐（后端是 Python，跨运行时收益不抵运维成本）。

| -------------------------------------------------------------------- | ----- | --------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |

| [short-video-maker](https://github.com/gyoridavid/short-video-maker) | 1.2k  | MIT                   | TypeScript | MCP 协议驱动的短视频生成                                                                                                    | Agent 化调用方式参考                                                      |

### 4.2 editly schema 摘要（README 核实）

```
{
  defaults: { transition: { name, duration, audioInCurve, audioOutCurve } },
  clips: [
    {
      duration,
      transition,          // 本片段结尾处的转场
      layers: [ { type: video|image|title|subtitle|audio, ... } ]  // 后者叠加在前者之上
    }
  ]
}
```

要点：模板 = 一份可序列化的 JSON + 引用的资源文件；`defaults` 提供全局兜底、片段级可覆盖；图层顺序即叠放顺序。这与本项目 compose 步骤的声明式配置思路完全一致。

### 4.3 落地建议

- **P1/P2**：借鉴 editly schema，把现有 compose 配置升级为可保存、可分享的"模板描述文件"（JSON + 资源包）。模板市场 = 模板 JSON 的增删改查，不绑定任何第三方运行时，渲染仍走自有 FFmpegCompose。
- **不引入 Remotion**：能力虽强，但公司使用需付费许可，且渲染需 Node/Chromium 集群，与 Python 后端割裂。

## 5. 画面切换（转场）效果方向

### 5.1 候选路线对比

| 路线                            | 项目/能力                                                                                                                     | Stars | 评估                                                                                                                                                |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ----- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **FFmpeg 内置 `xfade`（推荐）** | FFmpeg 4.3+ 自带约 50 种转场（fade / wipeleft / slideright / circleopen / pixelize / radial …），另支持 `custom` 表达式自定义 | —     | **零新依赖**，与现有 `FFmpegCompose` 子进程链路直接兼容，只需改 filter graph                                                                        |
| GLSL 转场合集                   | [gl-transitions](https://github.com/gl-transitions/gl-transitions)                                                            | 2.1k  | 行业事实标准（约 80 种效果，editly 即接它）；但接入需 WebGL/OpenGL 管线；各效果文件**独立授权**，逐个确认后可将其数学公式翻译为 xfade custom 表达式 |
| FFmpeg 自定义 filter            | [ffmpeg-gl-transition](https://github.com/transitive-bullshit/ffmpeg-gl-transition)                                           | 720   | 需要**自行编译 FFmpeg**，部署运维成本高，**不推荐**                                                                                                 |
| MoviePy clip 级转场             | MoneyPrinterTurbo `video_effects`（fadein/fadeout/slidein/slideout/zoomin/zoomout）                                           | —     | 低成本参考路径；但本项目合成链路是原生 ffmpeg 子进程而非 MoviePy，优先级低于 xfade                                                                  |

### 5.2 落地建议

- **P0.5（建议提级，成本极低）**：在 `_compose_command()` 的片段拼接处接入 `xfade`，预设 8~~10 种常用转场（淡入淡出、左右滑动、圆形展开、闪黑、模糊过渡等），每种固定 0.3~~0.5s 时长。前端剪辑台 V2 的"片段"Tab 增加转场选择器（片段之间的"+"交界点选择转场类型）。
- 注意 `xfade` 要求两路输入分辨率/帧率一致——现有链路已在合成前统一归一到目标画幅，天然满足。
- 音频侧配合 `acrossfade` 做等长交叉淡化，避免转场处爆音。
