- 版本：v1.0

- 关联文档：[06-最终开发文档](../architecture/06-最终开发文档.md)
- 方案：**A 改良版 —— 激活码即注册（服务端验证）**

---

## 一、业务目标

将现有"开放注册"改为"激活码准入制"：

1. **无码不可用**：用户必须持有有效激活码才能注册开户
2. **一码一户**：激活码绑定唯一用户，激活后不可转让/复用
3. **码即商品**：不同面额/时长的激活码对应不同套餐（点数包 / 月卡 / 季卡 / 年卡）
4. **续费 = 新码**：已注册用户输入新激活码追加额度或续期
5. **管理后台**：运营可批量生码、查看使用状态、作废/冻结

## 二、激活方式决策：服务端验证 vs 本地验证

### 2.1 结论：**纯服务端验证，客户端零密钥逻辑**

| 对比维度   | 本地验证（离线激活）                   | 服务端验证（在线激活）✅       |
| ---------- | -------------------------------------- | ------------------------------ |
| 破解风险   | 高：客户端持有校验逻辑，可逆向 patch   | 极低：客户端仅传码，服务端判定 |
| 一码多卖   | 无法防止（本地无法同步状态）           | 天然防止（DB 原子更新）        |
| 离线使用   | 支持                                   | 不支持（需联网）               |
| 实现复杂度 | 高（需非对称签名 + 机器指纹 + 反调试） | 低（标准 API 调用）            |
| 适用场景   | 桌面端买断制软件                       | **SaaS / 在线服务** ✅         |

### 2.2 为什么本项目必须用服务端验证

1. **我们是线上 SaaS**：所有核心能力（LLM 文案、声音克隆、数字人合成、多平台发布）均依赖服务端 API，客户端无法脱离服务器独立运行
2. **额度扣费在服务端**：即使绕过激活校验，没有合法 JWT 就无法调用任何业务 API
3. **天然防破解**：激活码验证只是"发放 JWT 的前置门槛"，真正的安全屏障是 JWT + 额度系统，攻击者即使伪造激活状态也无法获得服务端资源

### 2.3 安全架构总览

```
┌─────────────────────────────────────────────────────────┐
│                    客户端（前端）                          │
│  输入激活码 + 设置密码 → POST /auth/activate             │
│  获得 JWT → 后续所有 API 携带 Bearer Token               │
└───────────────────────────┬─────────────────────────────┘
                            │ HTTPS
┌───────────────────────────▼─────────────────────────────┐
│                    服务端（FastAPI）                       │
│                                                         │
│  ┌─────────────┐    ┌──────────────┐    ┌────────────┐  │
│  │ 激活码验证   │───→│ 创建用户+发JWT│───→│ 发放额度   │  │
│  │ (DB原子操作) │    │ (auth模块)    │    │ (billing)  │  │
│  └─────────────┘    └──────────────┘    └────────────┘  │
│                                                         │
│  安全层：                                                │
│  • 激活码 HMAC 签名校验（防伪造）                         │
│  • 频率限制（防爆破）                                    │
│  • 一码一户（DB UNIQUE + 事务）                          │
│  • 码状态机（unused→used，不可逆）                       │
│  • 所有业务 API 需 JWT（激活只是入口）                    │
└─────────────────────────────────────────────────────────┘
```

## 三、安全设计（防破译 / 防滥用）

### 3.1 激活码生成算法

```
格式：ORAL-XXXX-XXXX-XXXX-XXXX-XXXX（20 位有效字符，不含前缀）

生成过程：
1. payload = {batch_id, seq, plan_type, quota, created_ts}
2. raw = base32(payload_bytes)  → 取 16 字符
3. checksum = HMAC-SHA256(raw, server_secret)[:4] → 4 字符校验位
4. code = "ORAL-" + raw[:4] + "-" + raw[4:8] + "-" + raw[8:12] + "-" + raw[12:16] + checksum[:4]
```

- **服务端密钥签名**：每个码包含 HMAC 校验位，伪造码无法通过签名验证
- **不可逆推**：即使获得大量有效码，无法反推 server_secret 生成新码
- **批次溯源**：batch_id 编码在码内，泄露时可定位渠道并批量作废

### 3.2 防爆破策略

| 措施     | 实现                                                     |
| -------- | -------------------------------------------------------- |
| 频率限制 | 同一 IP 每分钟最多 5 次激活尝试；同一设备指纹每分钟 3 次 |
| 验证码   | 连续 3 次失败后触发图形验证码（预留接口）                |
| 码空间   | 16 字符 base32 = 32^16 ≈ 1.2×10^24，暴力不可行           |
| 锁定机制 | 单 IP 日累计 20 次失败 → 封禁 24h                        |
| 审计日志 | 所有激活尝试（成功/失败）写入 audit_log                  |

### 3.3 防转让 / 防共享

| 措施     | 说明                                        |
| -------- | ------------------------------------------- |
| 一码一户 | 激活后 `bound_user_id` 写入，不可更改       |
| 设备绑定 | 激活时记录设备指纹，可配置单设备/多设备上限 |
| 登录互踢 | 复用现有 `single_session_kick` 配置         |
| 异常检测 | 同账号短时间多 IP 登录 → 告警（预留）       |

### 3.4 为什么不需要本地加密/机器码绑定

传统桌面软件需要"机器指纹 + 本地 License 文件"是因为软件本体在用户机器上运行，可被逆向。

我们的场景：

- **核心逻辑全在服务端**：前端只是 UI 壳，所有 AI 能力通过 API 调用
- **JWT 即 License**：没有合法 token，前端无法获取任何数据
- **激活码只是"开户凭证"**：即使泄露已使用的码，也无法再次激活（状态已变更）

因此：**无需在客户端存储任何密钥、无需机器码绑定、无需反调试**。安全性完全由服务端 JWT + 额度系统保障。

## 六、核心业务流程

### 6.1 新用户激活注册

```
用户输入激活码
  → 前端调用 POST /auth/validate-code（实时校验，展示套餐信息）
  → 用户填写手机号 + 密码 + 昵称
  → 前端调用 POST /auth/activate
  → 服务端：
     1. 验证码签名（HMAC 校验位）
     2. 查 DB：code.status == "unused" && 未过期
     3. 检查手机号唯一性
     4. 事务内：
        a. 创建 User（activated_at=now, plan_type, plan_expires_at）
        b. 更新 code（status="used", bound_user_id, activated_at）
        c. 创建 QuotaAccount + 发放额度
        d. 创建默认 IP 档案
        e. 写入 user_subscriptions 记录
        f. 写入 audit_log
     5. 签发 JWT 双令牌
  → 返回 tokens + user info
```

### 6.2 已登录用户续费

```
用户输入新激活码
  → POST /auth/redeem（携带 JWT）
  → 服务端：
     1. 验证码签名 + 状态
     2. 事务内：
        a. 追加额度（balance += quota_amount）
        b. 续期（plan_expires_at = max(当前到期, now) + duration_days）
        c. 更新码状态
        d. 写入 user_subscriptions
     3. 返回新余额 + 到期时间
```

### 6.3 套餐过期处理

```
定时任务（每日 00:05）：
  → 扫描 plan_expires_at < now 且 status=active 的用户
  → 标记 plan_type = "expired"
  → 不删除数据、不禁用登录
  → 用户仍可登录，但：
     • 额度扣费接口返回 402 + 提示"套餐已到期，请兑换新激活码"
     • 前端展示到期提醒 + 兑换入口
```

## 七、套餐体系设计

| 套餐   | plan_type | 额度      | 有效期 | 适用场景     |
