## 一、业务目标

用户在「账号管理」绑定抖音账号后，系统自动拉取该账号的私信消息，并支持：

1. **消息聚合展示**：所有绑定账号的私信统一收口到前端「私信中心」
2. **建议回复**：基于 IP 人设、模板或 LLM 生成待人工确认的建议
3. **官方页面人工回复**：桌面端按账号打开隔离的抖音官方页面，由用户完成发送
4. **规则引擎**：关键词匹配 / 全量 LLM / 模板建议三种策略可配

当前版本固定 `IM_LISTEN_ONLY=true`。公开 HTTP 接口不提供发送、重试或自动发送授权；
历史出站状态和内部兼容代码只用于审计与回归，不能解释为当前可用业务能力。

## 二、技术架构

### 2.1 当前核心技术链路

```
账号 Cookie（sessionid）
  → WebSocket 长连接 wss://frontier-im.douyin.com/ws/v2（实时接收私信）
  → Protobuf 解码消息体（文本/图片/语音/表情/视频分享）
  → 消息入库 + 事件推送前端
  → 匹配建议回复规则
  → 生成 suggested 记录
  → 用户在按账号隔离的抖音官方页面人工发送
```

### 2.2 模块定位

```
server/app/modules/im/          ← 业务模块（标准六件套）
server/app/providers/im/        ← Provider 抽象层（抖音 IM 实现）
server/app/workers/im_listener.py  ← WebSocket 监听常驻任务
apps/web/src/pages/Im*.tsx      ← 前端私信中心页面
```

### 2.3 与现有模块关系

| 依赖模块 | 关系 |
|----------|------|
| `publish` | 复用 `PublishAccount` 表的 Cookie/session 数据 |
| `ipasset` | 读取 IP 人设定义注入 LLM 回复 prompt |
| `providers/llm` | 调用 LLMProvider 生成智能回复 |
| `notify` | 新消息事件通过 WS 网关推送前端 |
| `core/events` | 领域事件总线（CHANNEL_IM 新增） |

## 四、API 设计

### 4.1 会话管理

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/im/conversations` | 会话列表（分页，支持 `search` 检索昵称/UID/消息和 `accountId` 过滤） |
| GET | `/im/conversations/{id}/messages` | 某会话的消息列表（分页，支持 `search` 全文子串过滤） |
| PUT | `/im/conversations/{id}/read` | 标记已读 |
| POST | `/im/messages/{id}/takeover` | 将历史发送失败记录标记为人工接管 |

`/im/conversations/{id}/send` 和 `/im/messages/{id}/retry` 不在公开路由中。
规则统一以 `deliveryMode=suggestion` 保存；即使数据库存在历史 `auto` 规则，只读运行时
也只生成 `suggested` 记录并标记 `ListenOnlyMode`，不会进入发送队列。

### 4.2 建议回复规则

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/im/rules` | 规则列表 |
| POST | `/im/rules` | 创建规则 |
| PUT | `/im/rules/{id}` | 更新规则 |
| DELETE | `/im/rules/{id}` | 删除规则 |
| PUT | `/im/rules/{id}/toggle` | 启用/禁用 |

### 4.3 监听控制

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/im/listener/start` | 启动指定账号的消息监听 |
| POST | `/im/listener/stop` | 停止监听 |
| GET | `/im/listener/status` | 所有账号监听状态 |

### 4.4 只读监听急停

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/admin/v1/im/kill-switch` | 管理员查询全局急停状态 |
| PUT | `/api/admin/v1/im/kill-switch` | 管理员全局停止或恢复灰度监听 |

全局停止后，现有监听意图会改为断开，新监听请求返回 `IM_GLOBAL_STOPPED`，监听 Worker
不再恢复连接。急停同时取消历史版本遗留的 `scheduled` 消息；恢复开关只恢复灰度监听资格，
不会开放服务端发送。

### 4.5 历史数据与保留

会话按 `last_message_at + id` 稳定倒序，消息按 `created_at + id` 稳定倒序；所有查询先按
`user_id` 隔离，账号过滤和文本检索不得放宽归属条件。同一账号、用户和远端 UID 只能存在一个会话，
并发插入冲突时回读已有会话，消息不落入重复会话。

默认保留 90 天历史。独立监听 Worker 每 24 小时执行一次有界批量清理；只删除超期的终态消息和无消息会话，
`scheduled`/`pending`/`failed` 任务始终保留。保留天数和清理周期分别由 `IM_HISTORY_RETENTION_DAYS`、
`IM_CLEANUP_INTERVAL_HOURS` 配置。

### 4.6 灰度准入与监控

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/admin/v1/im/gray/accounts` | 管理员查询灰度账号名单 |
| PUT | `/api/admin/v1/im/gray/accounts/{accountId}` | 加入灰度名单 |
| DELETE | `/api/admin/v1/im/gray/accounts/{accountId}` | 移出名单并停止监听、取消遗留排队消息 |
| GET | `/api/admin/v1/im/monitoring?hours=24` | 查询连接、掉线、发送、限额和风控聚合指标 |
| POST | `/api/admin/v1/im/monitoring/incidents` | 管理员登记平台封控或风险事件 |

`IM_GRAY_ENFORCED=true` 默认启用。API 启动监听时检查灰度名单；独立监听 Worker 的恢复、
连接意图检查、账号 Session 加载和入站消息处理也会再次检查，避免遗留状态或直接任务调用绕过
allowlist。监控事件与业务事务隔离写入，监控写入失败会记录错误，但不回滚已成功的入站处理。

管理员新增灰度账号受 `IM_GRAY_MAX_ACCOUNTS` 受控上限约束，默认最多 20 个。原始监控事件按
`IM_METRIC_RETENTION_DAYS` 独立保留，默认 14 天；会话历史继续使用 `IM_HISTORY_RETENTION_DAYS`。
连续七天验收流程、阈值和证据命名见 [13-第三阶段七天灰度验收](13-第三阶段七天灰度验收.md)。

## 五、Provider 抽象层设计

```python
# providers/im/base.py
class IMProvider(Protocol):
    name: str
    platform: str

    async def connect(self, session: dict) -> "IMConnection": ...
    async def create_conversation(self, session: dict, to_uid: int) -> dict: ...

class IMConnection(Protocol):
    """WebSocket 长连接抽象"""
    async def listen(self, on_message: Callable) -> None: ...
    async def close(self) -> None: ...
    @property
    def is_alive(self) -> bool: ...
```

实现：
- `providers/im/douyin_im.py`：整合 DouYin_Spider 的 WebSocket + Protobuf 逻辑
- 当前生产绑定只使用连接和监听能力；内部历史发送方法不由 HTTP/API Client 暴露
- 未配置真实 Provider 时 fail-closed；单元测试使用局部 Fake，不注册可写入 `sent` 的运行时 Mock

## 六、建议回复策略引擎

```
收到私信（direction=in）
  → 加载该账号/全局的 enabled 规则（按 priority 排序）
  → 逐条匹配：
     1. keyword 模式：正则/包含匹配 trigger_pattern
     2. all 模式：匹配所有消息
     3. llm 模式：同 all，但回复由 LLM 生成
  → 命中规则后：
     - reply_mode=template → 生成 reply_template 建议
     - reply_mode=llm → 调用 LLMProvider.rewrite()，注入 IP 人设 prompt
  → 内容审核
  → 记录 im_messages（direction=out, send_status=suggested）
  → 用户打开抖音官方页面人工发送
```

## 八、风控与安全设计

| 策略 | 实现 |
|------|------|
| 被动优先 | 默认仅回复对方先发起的私信 |
| Cookie 心跳 | 每 30min 调轻量 API 验证有效性 |
| 失效告警 | Cookie 被平台明确拒绝 → 停止监听、取消遗留排队消息、标记账号 expired，并发送站内信引导重新授权 |
| 心跳容错 | 网络超时、5xx 或非 JSON 响应视为巡检暂不可用，60s 后重试，不误判为 Cookie 失效 |
| 会话隔离 | 桌面官方页面按账号使用独立、哈希化的数据目录 |
| 紧急停止 | 全局 Kill Switch 仅管理员可操作，并阻断新监听意图 |
| 内容审核 | 建议内容经过合规检测（禁止引流/敏感词） |

## 十、验收标准

1. 绑定抖音账号后，点击「开始监听」，前端实时展示收到的私信
2. 配置关键词或 LLM 规则后，对方私信生成 `suggested` 建议，不调用发送 Provider
3. 用户点击人工回复时，桌面端按当前账号打开抖音官方页面
4. 两个账号的官方页面使用不同会话目录，不串用 Cookie 或登录态
5. Cookie 过期后，前端弹出「登录态失效」告警，监听自动停止
6. 所有消息记录可在前端「私信中心」查看历史
7. 历史 `deliveryMode=auto` 规则在只读模式下仍只能生成建议，不能进入发送队列
8. 全局急停后，监听断开、新监听被拒绝、遗留排队消息被取消
9. 公开 OpenAPI 和 API Client 不包含发送、重试或自动发送授权入口
10. 100+ 条消息下分页顺序稳定，搜索和账号过滤不跨用户
