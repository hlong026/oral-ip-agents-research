## 一、业务目标

用户在「账号管理」绑定抖音账号后，系统自动拉取该账号的私信消息，并支持：
1. **消息聚合展示**：所有绑定账号的私信统一收口到前端「私信中心」
2. **AI 自动回复**：基于 IP 人设 + LLM 生成回复，模拟人工节奏发送
3. **半自动模式**：AI 生成建议回复 → 用户确认 → 发送（降低风控）
4. **规则引擎**：关键词匹配 / 全量 LLM / 模板回复三种策略可配

## 二、技术架构

### 2.1 核心技术链路（来自 DouYin_Spider 验证）

```
账号 Cookie（sessionid）
  → WebSocket 长连接 wss://frontier-im.douyin.com/ws/v2（实时接收私信）
  → Protobuf 解码消息体（文本/图片/语音/表情/视频分享）
  → 消息入库 + 事件推送前端
  → 匹配自动回复策略
  → POST https://imapi.douyin.com/v1/message/send（Protobuf 发送回复）
```

### 2.2 模块定位

```
server/app/modules/im/          ← 业务模块（标准六件套）
server/app/providers/im/        ← Provider 抽象层（抖音 IM 实现）
server/app/workers/im_listener.py  ← WebSocket 监听常驻任务
apps/web/src/pages/Im*.tsx      ← 前端私信中心页面
```

### 2.3 与现有模块关系

| 依赖模块 | 关系 |
|----------|------|
| `publish` | 复用 `PublishAccount` 表的 Cookie/session 数据 |
| `ipasset` | 读取 IP 人设定义注入 LLM 回复 prompt |
| `providers/llm` | 调用 LLMProvider 生成智能回复 |
| `notify` | 新消息事件通过 WS 网关推送前端 |
| `core/events` | 领域事件总线（CHANNEL_IM 新增） |

## 四、API 设计

### 4.1 会话管理

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/im/conversations` | 会话列表（分页，支持 `search` 检索昵称/UID/消息和 `accountId` 过滤） |
| GET | `/im/conversations/{id}/messages` | 某会话的消息列表（分页，支持 `search` 全文子串过滤） |
| POST | `/im/conversations/{id}/send` | 手动发送消息 |
| PUT | `/im/conversations/{id}/read` | 标记已读 |
| POST | `/im/messages/{id}/retry` | 重试一条发送失败的消息 |
| POST | `/im/messages/{id}/takeover` | 将发送失败消息切换为人工接管 |

出站消息必须返回 `sendStatus`、`sendError`、`retryCount` 和
`manualTakeover`。只有 Provider 明确确认成功时状态才可写为 `sent`；网络错误、
平台拒绝或未确认响应必须写为 `failed`，不得创建伪成功记录。

规则的 `deliveryMode` 默认是 `suggestion`，只生成待人工确认的建议回复。设置为
`auto` 也必须先通过敏感内容、违规承诺、联系方式和提示注入审核；未通过的消息以
`blocked` 状态留痕，不进入发送队列。

### 4.2 自动回复规则

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/im/rules` | 规则列表 |
| POST | `/im/rules` | 创建规则 |
| PUT | `/im/rules/{id}` | 更新规则 |
| DELETE | `/im/rules/{id}` | 删除规则 |
| PUT | `/im/rules/{id}/toggle` | 启用/禁用 |

### 4.3 监听控制

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/im/listener/start` | 启动指定账号的消息监听 |
| POST | `/im/listener/stop` | 停止监听 |
| GET | `/im/listener/status` | 所有账号监听状态 |

### 4.4 自动发送授权与急停

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/im/automation/status` | 查询当前用户各账号的风险授权状态 |
| POST | `/im/automation/authorize` | 确认指定版本风险协议并授权单账号自动回复 |
| POST | `/im/automation/{accountId}/disable` | 单账号紧急停止并取消其排队消息 |
| GET | `/api/admin/v1/im/kill-switch` | 管理员查询全局急停状态 |
| PUT | `/api/admin/v1/im/kill-switch` | 管理员全局停止或恢复受控自动回复 |

自动回复默认关闭。即使规则的 `deliveryMode=auto`，仍需同时满足账号已确认当前版本风险协议、
全局 Kill Switch 已由管理员开放；发送任务执行前会再次检查两级门禁。全局或单账号急停会把
尚未发送的 `scheduled` 消息改为 `canceled`，已在途的平台请求不能承诺撤回。

### 4.5 历史数据与保留

会话按 `last_message_at + id` 稳定倒序，消息按 `created_at + id` 稳定倒序；所有查询先按
`user_id` 隔离，账号过滤和文本检索不得放宽归属条件。同一账号、用户和远端 UID 只能存在一个会话，
并发插入冲突时回读已有会话，消息不落入重复会话。

默认保留 90 天历史。独立监听 Worker 每 24 小时执行一次有界批量清理；只删除超期的终态消息和无消息会话，
`scheduled`/`pending`/`failed` 任务始终保留。保留天数和清理周期分别由 `IM_HISTORY_RETENTION_DAYS`、
`IM_CLEANUP_INTERVAL_HOURS` 配置。

### 4.6 WebSocket 事件（复用 /ws/tasks 网关）

```json
// 新私信到达
{"kind": "im_new_message", "userId": "...", "conversationId": "...", "message": {...}}
// 自动回复已发送
{"kind": "im_auto_replied", "userId": "...", "conversationId": "...", "reply": "..."}
// 监听状态变更
{"kind": "im_listener_status", "userId": "...", "accountId": "...", "status": "listening"}
```

## 五、Provider 抽象层设计

```python
# providers/im/base.py
class IMProvider(Protocol):
    name: str
    platform: str

    async def connect(self, session: dict) -> "IMConnection": ...
    async def send_message(self, session: dict, conversation_id: str,
                           conversation_short_id: str, ticket: str,
                           content: str) -> bool: ...
    async def create_conversation(self, session: dict, to_uid: int) -> dict: ...

class IMConnection(Protocol):
    """WebSocket 长连接抽象"""
    async def listen(self, on_message: Callable) -> None: ...
    async def close(self) -> None: ...
    @property
    def is_alive(self) -> bool: ...
```

## 六、自动回复策略引擎

```
收到私信（direction=in）
  → 加载该账号/全局的 enabled 规则（按 priority 排序）
  → 逐条匹配：
     1. keyword 模式：正则/包含匹配 trigger_pattern
     2. all 模式：匹配所有消息
     3. llm 模式：同 all，但回复由 LLM 生成
  → 命中规则后：
     - 检查 daily_limit（当日该规则已回复数）
     - 随机延迟 delay_min ~ delay_max 秒
     - reply_mode=template → 直接发送 reply_template
     - reply_mode=llm → 调用 LLMProvider.rewrite()，注入 IP 人设 prompt
  → 发送回复 → 记录 im_messages（direction=out, auto_replied=True）
  → 推送前端事件
```

## 八、风控与安全设计

| 策略 | 实现 |
|------|------|
| 频率限制 | 单账号每分钟 ≤ 3 条回复，每日 ≤ 50 条（可配） |
| 随机延迟 | 每条回复延迟 3~30s（正态分布），模拟人工 |
| 被动优先 | 默认仅回复对方先发起的私信 |
| Cookie 心跳 | 每 30min 调轻量 API 验证有效性 |
| 失效告警 | Cookie 被平台明确拒绝 → 停止监听、取消待发送回复、禁用账号自动回复、标记账号 expired，并发送站内信引导重新授权 |
| 心跳容错 | 网络超时、5xx 或非 JSON 响应视为巡检暂不可用，60s 后重试，不误判为 Cookie 失效 |
| 风险授权 | 用户启用自动回复前须勾选版本化风险协议；授权按账号隔离 |
| 紧急停止 | 单账号急停由账号所有者控制；全局 Kill Switch 仅管理员可操作 |
| 内容审核 | 回复内容经过 LLM 合规检测（禁止引流/敏感词） |

## 十、验收标准

1. 绑定抖音账号后，点击「开始监听」，前端实时展示收到的私信
2. 配置关键词规则（如"价格"），对方发送含"价格"的私信后 3~30s 内收到自动回复
3. 配置 LLM 规则，对方发送任意私信后收到基于 IP 人设的智能回复
4. Cookie 过期后，前端弹出「登录态失效」告警，监听自动停止，待发送消息取消，且人工重试不调用平台 Provider
5. 每日回复达到上限后自动停止，次日恢复
6. 所有消息记录可在前端「私信中心」查看历史
7. 未确认风险协议或全局开关处于停止状态时，自动规则只能生成建议，不能进入发送队列
8. 单账号或全局急停后，排队消息立即标记为取消，任务执行时不得调用平台 Provider
9. 100+ 条消息下分页顺序稳定，搜索和账号过滤不跨用户，超期清理不删除可发送或可重试任务
