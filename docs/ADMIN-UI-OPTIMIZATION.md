# 管理控制台后台设计优化方案

## 📊 现状诊断

### 核心问题

经过详细分析，当前管理控制台存在以下主要问题：

1. **技术术语过多，用户理解成本高**
   - SKU、sku_type、audience、unit_size、billing_unit 等英文字段
   - 内部技术概念（如 bps 毛利点、version_id）直接暴露给用户
   - 缺乏业务友好的中文解释和引导

2. **配置项过于复杂**
   - 套餐 SKU 配置需要填写 15+ 个字段，其中很多是技术人员关心的技术细节
   - 积分价格版本需要为每个模块配置 unitSize、pointsPerUnit、minimumPoints、internalCostCentsPerUnit、targetMarginBps 等 7-8 个参数
   - 激活码生成虽然简单但绑定关系不够直观

3. **信息层级混乱**
   - 重要信息（名称、价格）与次要信息（排序、时间戳）混在一起
   - 前端显示与后端配置的映射关系不清晰
   - 没有清晰的"快速配置模板"和"高级配置"分离

4. **操作流程繁琐**
   - SKU 创建需要先了解完整的业务模型才能正确配置
   - 价格版本需要逐个模块单独配置单位、大小、积分等
   - 缺少批量操作向导

---

## 🎯 优化目标

**核心原则**：
1. **用户友好**：使用业务语言替代技术术语
2. **分层配置**：区分"快速上手"和"高级设置"
3. **减少认知负担**：默认值 + 智能推荐 + 实时预览
4. **可视化引导**：用图表和示例辅助理解

## ✅ 具体优化方案

### 一、套餐 SKU 配置优化

#### 问题对比

| 当前字段 | 问题 | 优化方案 |
|---------|------|---------|
| `code` (SKU 编码) | 技术内部标识 | ✅ 改为"套餐 ID/编码"，自动生成 UUID 或允许输入可读 ID 如 vip_pro |
| `skuType` = "annual_bundle" | 无意义的英文枚举 | ✅ 下拉选择：**「体验版」** / **「订阅版」** / **「一次性买断」** / **「企业内部版」** |
| `audience` = "public" | 内部用户分类 | ✅ 切换开关：**「面向公众」** / **「仅限内部员工」** |
| `durationDays` = 365 | 纯数字，含义不明 | ✅ 服务周期：**「每月」** / **「每季度」** / **「每年」** / **「永久」**（自动计算 durationDays） |
| `monthlyPoints` / `oneTimePoints` | 两个字段难以理解 | ✅ 单选切换：**「按月扣费型」**（填月积分） / **「一次性买断型」**（填总积分） |
| `listPriceCents` / `displayPriceCents` | 单位是分，容易出错 | ✅ 单位改成元，自动换算分；添加格式化输入器 |
| `maxConcurrency` | 技术限制 | ✅ "最大并发任务数" + 滑动条 |
| `entitlements` = "digital_human,voice_clone" | 逗号分隔的英文编码 | ✅ **勾选式权益配置**：展示可用权益列表，勾选即选 |
| `maxResolution` | 分辨率编码 | ✅ 下拉选择清晰度：**「标清 720p」** / **「高清 1080p」** / **「超清 2K」** / **「超清 4K」** |

#### 数据字典转换层（后端实现）

在 API 层增加转换逻辑，将业务语言转换为技术字段：

```python
# server/app/modules/catalog/transformers.py

def to_model(data: PlanCreateIn) -> PlanVersion:
    """业务请求 → ORM 模型"""
    
    # 服务周期转换
    if data.servicePeriod == "trial":
        sku_type = "trial"
        duration_days = 7
    elif data.servicePeriod == "monthly":
        sku_type = "annual_bundle"  # reuse existing type name
        duration_days = 30
    elif data.servicePeriod == "yearly":
        sku_type = "annual_bundle"
        duration_days = 365
    else:  # lifetime
        sku_type = "lifetime_bundle"
        duration_days = 365 * 10  # 虚拟 10 年
    
    # 适用对象转换
    audience = "internal" if data.isInternal else "public"
    
    # ... 其他转换
```

**好处**：
- 前端完全屏蔽技术细节
- 后端维护统一的领域模型
- 新增类型时只需改一处

### 二、积分价格版本优化

#### 当前痛点

一个模块有**8 个参数**需要配置：
- `module`: 模块编码（技术字段）
- `displayName`: 显示名称（已有中文）
- `billingUnit`: 计费单位（per_1k_tokens 这种英文）
- `unitSize`: 单位大小（1000？）
- `pointsPerUnit`: 每单位积分（6？）
- `minimumPoints`: 最低积分（6？）
- `internalCostCentsPerUnit`: 内部成本（30 分？）
- `targetMarginBps`: 目标毛利率（6000bps = 60%？）

这对运营人员非常困惑！

#### 简化方案

**思路**：分成两步，先配"对外计费规则"，再配"内部成本利润率"

#### 第一步：对外计费规则（核心）

```
【AI 选题生成】
计费单位：
├─ 按次数    (每次提交算一次)
├─ 按字符数  (每 1000 字符)
└─ 按 Token   (每 1000 tokens) ← 当前选择

[  1000  ] 个为一单位
[    6   ] 积分/单位
[    6   ] 积分起充（最低消费）
  
💡 用户端说明：每 1000 Tokens 扣 6 积分
```

**智能提示**：
- 当单位改成"按 Token"，自动填充 unitSize = 1000
- 当单位改成"按字数"，自动填充 unitSize = 1000（假设 1 字≈1Token）

#### 第二步：内部成本配置（高级选项，折叠默认隐藏）

```
⚙️ 高级选项（点击展开）
─────────────────────────────────

【内部成本】¥0.30 /单位
提示：这是该次任务的云服务成本（美元转人民币）

【目标利润率】60%
提示：建议维持 ≥50% 以保证盈利

【实际利润率】✅ 58.3% (正常)
计算公式：(售价 - 成本) / 售价 × 100%
```

**好处**：
1. 运营人员先配置对外计费，符合业务思维
2. 内部成本作为高级选项，避免初学者混淆
3. 自动计算利润率，提供健康度提示

```

├─ 套餐 SKU
├─ 积分价格

**商业化中心**
```
├─ 📦 套餐管理
│  ├─ 所有套餐
│  └─ 创建新套餐（重点入口）
│
├─ 💰 价格配置

│
├─ 🎫 激活码管理

│
└─ 📊 经营报表
   ├─ 套餐销售统计

**关键变化**：
1. 命名更业务化（SKU→套餐，Price Versions→价格配置）

3. 扩展性更好（后续可增加报表功能）

## 💬 总结

**核心思想**：
1. **用户视角而非开发者视角**：忘记技术实现，思考业务场景
2. **渐进式披露**：简单事情简单做，复杂需求深入配置
3. **智能默认值**：90% 的场景用默认值就能完成，10% 特殊场景走高级模式
4. **实时反馈**：所见即所得，减少猜测和试错
